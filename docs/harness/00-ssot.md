# 00. SSOT

> 이 문서는 저장소에서 어떤 질문을 어디에서 판단할지만 정한다.
>
> 실제 내용은 각 원본에 두며, 여기에는 복사하지 않는다.

## 0. 원칙

1. 책임 영역마다 원본은 하나만 둔다.
2. 참고 문서와 원본이 다르면 원본을 따른다.
3. 도메인·아키텍처 기준이 바뀌면 원본을 먼저 수정한다.
4. 원본이 없는 영역의 결정은 임의로 정하지 않는다. 원본이 없다고 보고하고 사람에게 묻는다.
5. 원본을 새로 만들거나 옮기면 이 표도 함께 갱신한다.

## 1. 책임별 원본

| 영역 | 원본 | 상태 |
|---|---|---|
| 재고 도메인 | `docs/01-requirements.md` | 원본 지정 |
| 아키텍처 | `docs/06-architecture.md` | 원본 지정 |
| 개별 작업 | 해당 GitHub Issue | 원본 지정 |
| 검증 규칙 | `docs/harness/02-verification.md` | 원본 지정 |
| 구현·검증 루프 | 없음 | 추후 생성 |

## 2. 책임 경계

### 재고 도메인

`docs/01-requirements.md`는 재고의 개념, 기능, 업무 규칙과 제품 완료 기준을 정한다.

기술 구조와 구현 방법은 다루지 않는다.

### 아키텍처

`docs/06-architecture.md`는 기술 스택, 파일 구조, 데이터 모델과 재고 처리 구조를 정한다.

재고의 업무 규칙 자체는 다루지 않는다. 그것은 `docs/01-requirements.md`의 몫이다.

### 개별 작업

해당 GitHub Issue는 이번에 무엇을 변경하고, 무엇을 만족하면 끝나는지를 정한다.

작업 중 도메인이나 아키텍처 결정이 바뀌면 Issue만 수정하지 않고 해당 원본을 먼저 갱신한다.

### 검증 규칙

`docs/harness/02-verification.md`는 무엇을 통과해야 변경이 끝난 것인지를 정한다.
검증 단계의 구성과 순서, 게이트와 경고의 구분, 검사 불능의 처리, 검증 환경, Issue 단위 검증의 형식을 다룬다.

검증 항목의 내용은 정하지 않는다. 재고 규칙은 `docs/01-requirements.md`, 구조 규칙은
`docs/06-architecture.md`, 보호 경로는 이 문서 5절, 이번 작업의 종료 조건은 Issue가 정한다.

검증 스크립트(`scripts/verify/` 등)와 `npm run verify`는 이 문서가 정한 판정을 실행하는 수단이다.
스크립트와 이 문서가 다르면 이 문서를 따르고 불일치를 보고한다.

## 3. 현재 없는 책임 영역

| 영역 | 정해야 할 것 | 계획 |
|---|---|---|
| 구현·검증 루프 | 검증 결과에 따라 언제 다시 시도하고, 몇 번까지 반복하며, 언제 사람에게 넘기는지 | 추후 생성 |

원본이 생기기 전까지 이 영역에 대한 판단은 임의로 정하지 않는다 (0절 4번).
원본이 생기면 1절 표의 원본과 상태를 함께 갱신한다 (0절 5번).

## 4. 충돌 정책

여기서 SSOT는 1절 표에 원본으로 지정된 문서를 말한다.

| 충돌 | 처리 |
|---|---|
| 참고 문서 ↔ SSOT | SSOT를 우선한다 |
| Issue ↔ SSOT | `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다 |
| SSOT ↔ SSOT | `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다 |

AI는 충돌이 발생할 경우 자신의 판단대로 행동하지 않는다.
어느 쪽이 옳아 보이더라도 위 표가 정한 처리 외에 스스로 한쪽을 골라 작업을 진행하지 않는다.

### `NEEDS_HUMAN` 선언

`NEEDS_HUMAN`은 자동화된 판단을 멈추고 사람에게 넘길 때 선언하는 상태다.

선언하면 다음을 지킨다.

1. 판단을 받기 전까지 그 충돌에 의존하는 변경은 하지 않는다. 무관한 작업은 계속한다.
2. 판단이 나오면 사람의 결정에 따라 해당 SSOT·Issue를 먼저 갱신하고 재개한다.

사람에게 판단을 요청할 때는 다음 네 가지를 적는다.

1. 충돌한 두 지점 — 파일과 절 번호, Issue 번호
2. 각각이 말하는 내용
3. 어느 쪽을 선택하느냐에 따라 달라지는 결과
4. 사람이 답해야 할 질문 한 줄

## 5. 보호 영역과 소유권

영역마다 AI의 읽기·변경 권한과 사람의 권한을 나눈다.

| 영역 | AI | 사람 |
|---|---|---|
| 애플리케이션 코드 | Issue 범위 안에서 수정 | 최종 승인 |
| Issue별 테스트 | 작성 · 수정 | 전제 검토 |
| 요구사항 · 아키텍처 | 읽기 | 변경 · 승인 |
| 하네스 핵심 규칙 | 읽기 | 변경 · 승인 |
| 검증 스크립트 | 실행 | 정책 변경 승인 |

이 저장소에서 각 영역이 가리키는 것은 다음과 같다.

| 영역 | 대상 |
|---|---|
| 애플리케이션 코드 | `src/`, `prisma/` |
| Issue별 테스트 | `tests/issues/` |
| 요구사항 · 아키텍처 | `docs/01-requirements.md`, `docs/06-architecture.md` |
| 하네스 핵심 규칙 | `docs/harness/`, `AGENTS.md`, `CLAUDE.md` |
| 검증 스크립트 | `scripts/verify/` |

AI는 사람의 변경 권한에 속한 영역을 직접 확정하지 않는다.
변경이 필요하면 변경안과 이유를 제시하고 사람의 승인을 기다린다.
사람의 명시적인 수정 요청은 해당 변경에 대한 승인으로 본다.

0절 3번의 "원본을 먼저 수정한다"는 원본 변경 권한까지 AI에게 준다는 뜻이 아니다.
AI는 변경안을 제시하고, 사람의 승인 후 원본을 먼저 갱신한다.

Issue 범위를 벗어나는 변경이 필요하면 작업을 진행하지 않고 사람에게 Issue 범위 변경을 요청한다.

### 보호 경로 검사

`npm run verify`의 첫 단계(Protected)가 이 절의 두 표를 읽어 보호 경로 변경을 검사한다.

- 검사 대상: 비교 기준과의 공통 조상 이후 바뀐 파일 전부 — 커밋된 변경, 스테이지, 작업 트리, 추적되지 않은 새 파일, 삭제
- 비교 기준: PR이면 그 PR의 base 브랜치, 아니면 `origin/main` (없으면 `main`)
- AI 칸이 "수정"·"작성"이 아닌 영역(읽기·실행)의 경로가 보호 경로다
- 승인 기록이 없는 보호 경로 변경이 하나라도 있으면 실패한다
- 이 절의 표를 읽을 수 없거나 비교 기준을 찾을 수 없으면 건너뛰지 않고 실패한다

### 승인 기록

보호 영역의 변경 승인은 검사가 확인할 수 있는 기록으로 남긴다.

| 방법 | 적는 곳 | 유효 범위 |
|---|---|---|
| 커밋 트레일러 | 작업 브랜치의 커밋 메시지에 `Approved-Protected: <경로> [<경로> ...]` | 로컬 · CI |
| 환경변수 | `ALLOW_PROTECTED="<경로> [<경로> ...]" npm run verify` | 그 로컬 실행 한 번 |

- 승인하는 것은 사람이다. AI는 사람이 그 변경을 명시적으로 요청했거나 승인한 경우에만 그 범위의 경로를 대신 기록한다.
- 경로는 저장소 루트 기준으로 적고, 여러 개는 공백이나 쉼표로 구분한다.
- 파일 경로는 그 파일만, 디렉터리 경로(`docs/harness/` 등)는 그 아래 전부를 승인한다.
- 모든 보호 경로를 한 번에 승인하는 표현은 없다. 승인은 경로를 적어서만 한다.
- 커밋 트레일러는 비교 기준 이후의 커밋에 있어야 유효하다. 승인 전용 빈 커밋으로 남겨도 된다.
- 승인은 변경 내용이 아니라 경로 단위다. 한 번 승인된 경로는 같은 작업 브랜치에서 그 뒤에 생기는 변경까지 덮는다.
  승인받은 뒤 그 경로를 승인 범위 밖의 내용으로 다시 바꿔야 하면, 커밋 전에 사람에게 다시 확인받는다.
- CI에서는 환경변수를 쓰지 않는다. CI를 통과시키려면 커밋 트레일러로 남긴다.
