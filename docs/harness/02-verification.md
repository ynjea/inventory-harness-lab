# 02. 검증 규칙

> 이 문서는 **무엇을 통과해야 변경이 끝난 것인지**만 정한다.
>
> 재고 규칙과 아키텍처 규칙 자체는 여기서 정하지 않는다. 그것은 `docs/01-requirements.md`와
> `docs/06-architecture.md`의 몫이고, 이 문서는 그 규칙들을 **언제 어떻게 판정하는지**를 정한다.
> 검증 스크립트는 이 문서가 정한 판정을 실행하는 수단이다.

## 0. 범위

| 정한다 | 정하지 않는다 |
|---|---|
| 공통 기계 검증의 단계 구성과 순서 | 재고 개념·기능·업무 규칙 (`01`) |
| 단계별로 무엇을 잡고 무엇을 안 잡는가 | 데이터 모델·재고 처리 구조 (`06`) |
| 게이트와 경고의 구분, 검사 불능의 처리 | 보호 경로와 승인 방법 (`00-ssot.md §5`) |
| 검증 환경 — 로컬과 CI, 검증용 DB | 이번 작업의 범위와 종료 조건 (GitHub Issue) |
| Issue 단위 검증의 형식 | 검증 결과에 따라 다시 시도하거나 멈추는 기준 (구현·검증 루프, `00-ssot.md §3` 추후 생성) |
| 검증 결과를 보고하는 기준 | |

검증 항목의 **내용**은 원본에서 온다. 이 문서에 도메인 수치나 불변식 목록을 옮겨 적지 않는다.

| 검증 항목의 출처 | 원본 |
|---|---|
| 자동 테스트로 지킬 불변식 | `06 §9` |
| 재고 변경 경로 규칙 | `06 §2` · `§4.1` · `§7.5` |
| 보호 경로와 승인 형식 | `00-ssot.md §5` |
| 이번 작업의 종료 조건 | 해당 Issue의 종료 조건 |

## 1. 검증의 층

| 층 | 무엇이 판정하나 | 현재 상태 |
|---|---|---|
| 기계 검증 | `npm run verify` (2절) | 있음 — 로컬과 CI에서 같은 것이 돈다 |
| 사람 판단 | 보호 경로 변경 승인 (`00-ssot.md §5`), 애플리케이션 코드 최종 승인 | 승인 기록 형식만 있음. 사람이 무엇을 확인하는지는 정하지 않았다 |
| LLM 검토 | — | 없음 |

사람이 무엇을 언제 확인하는지와 LLM 검토를 둘지는 구현·검증 루프 원본을 만들 때 함께 정한다.
그 전까지 이 둘을 이유로 판정을 바꾸지 않는다.

## 2. 공통 기계 검증 — `npm run verify`

모든 변경은 `npm run verify` 한 번으로 판정한다. 단계는 다음 순서로 돈다.

| # | 단계 | 실행 | 잡는 것 | 잡지 않는 것 |
|---|---|---|---|---|
| 1 | Protected | `scripts/verify/check-protected.ts` | 승인 없는 보호 경로 변경 (`00-ssot.md §5`) | 승인된 경로 안의 변경 내용이 맞는가 |
| 2 | Prepare | `scripts/reset-verify-db.ts` | — (판정이 아니라 준비. 실패하면 그 실행은 실패) | — |
| 3 | Types | `tsc --noEmit` | 타입 오류 | 실행 중 동작 |
| 4 | Lint | `eslint` | 코드 규칙 위반 | 아키텍처 경로 |
| 5 | Architecture Check | `scripts/check-architecture.ts` | 재고 변경이 `applyMovement()`를 거치지 않는 코드 (`06 §2` · `§4.1` · `§7.5`) | 줄을 나눠 쓰거나 변수로 우회한 호출 (줄 단위 검사) |
| 6 | Test | `vitest run` | `06 §9` 불변식, Issue별 종료 조건 (5절) | 화면 표시, 테스트가 없는 동작 |
| 7 | Build | `next build` | 빌드가 깨지는 변경 | 실행 중 동작 |

### 단계 중단

단계는 앞에서부터 차례로 돈다. 한 단계가 실패하면 그 실행은 거기서 멈추고 뒤 단계는 돌지 않는다.

뒤 단계가 돌지 않았다는 것은 그 단계를 통과했다는 뜻이 아니다. 앞 단계를 고친 뒤 처음부터 다시 돌린다.

### Prepare와 검증용 DB

- 검증은 개발용 `prisma/dev.db`가 아니라 검증용 `prisma/verify.db`에서 한다.
- Prepare는 실행마다 검증용 DB를 지우고 마이그레이션 · Prisma 클라이언트 생성 · 시드를 다시 돌린다.
  그래서 검증은 언제 돌려도 시드 직후의 같은 상태에서 시작한다.
- 검증은 개발용 DB를 지우거나 바꾸지 않는다. Prepare는 대상이 개발용 DB이면 멈춘다.
- 시드 날짜는 실행한 날 기준의 상대값이다. 같은 날에는 같은 데이터가 나오고, 날이 바뀌면 날짜 값만 함께 밀린다.

## 3. 게이트와 경고

게이트는 통과하지 못하면 그 변경이 완료가 아닌 판정이다. 경고는 완료를 막지 않는 판정이다.

| 구분 | 여기에 속하는 것 |
|---|---|
| 게이트 | `npm run verify`의 모든 단계 (2절) |
| 경고 | 현재 없음 |

하나라도 통과하지 못하면 그 변경은 완료가 아니다.

어떤 단계를 빼거나 경고로 낮추려면 이 문서를 먼저 고친다. 스크립트에서 조용히 빼거나 실패를 무시하는
것으로 대신하지 않는다.

### 검사 불능

단계가 판정을 내리지 못한 채 끝나면 — 환경이 갖춰지지 않았거나, 도구가 오류로 죽었거나,
원본을 읽지 못했거나, 비교 기준을 찾지 못했거나 — 실패로 본다.

판정하지 못한 것은 통과한 것이 아니다.

## 4. 검증 환경

| 환경 | 실행 | 조건 |
|---|---|---|
| 로컬 | `npm run verify` | Windows · macOS · Linux 모두 같은 명령. 셸 문법에 기대지 않는다 |
| CI | `.github/workflows/verify.yml` | PR, 그리고 `main` 푸시에서 `npm ci` 뒤 `npm run verify`를 돌린다 |

- CI 전용 단계를 따로 두지 않는다. 단계 순서는 `package.json`의 `verify` 한 곳에서 바꾸고, 바꾸면 이 문서 2절도 함께 고친다.
- CI는 Protected가 비교 기준을 구할 수 있도록 전체 이력을 받는다 (`fetch-depth: 0`).
- `npm test`를 따로 실행한 결과는 판정이 아니다. 검증용 DB를 거치지 않고 개발용 DB를 쓴다.

## 5. Issue 단위 검증

공통 기계 검증은 저장소 전체의 규칙을 본다. 이번 Issue의 종료 조건은 그 Issue의 전용 테스트가
판정한다.

| 항목 | 규칙 |
|---|---|
| 어디에 두나 | `tests/issues/issue-<번호>-<기능명>.test.ts` |
| 무엇을 적나 | Issue 폼 4번 칸에 종료 조건과 그것을 판정하는 테스트를 적는다 |
| 언제 도나 | 공통 기계 검증의 Test 단계에서 함께 돈다. 따로 돌리는 것은 판정이 아니다 |
| 종료 조건에 대응 테스트가 없으면 | 무엇으로 판정할지 Issue에 먼저 적고 돌린다 |
| 다른 Issue의 테스트 | 고치지 않는다. 고쳐야 하면 Issue 범위를 벗어난 것이다 |

---

## 6. 보고

- 실제로 돌린 단계와 그 결과만 보고한다. 돌리지 않은 단계를 통과로 적지 않는다.
- 실패하면 실패한 단계와 출력의 핵심 줄을 함께 적는다.
- 보호 경로가 승인으로 통과했다면 어느 경로가 어떤 기록(커밋 · 환경변수)으로 승인됐는지 적는다.
- 로컬과 CI 중 어디서 돌린 결과인지 밝힌다.

---

## 7. 알려진 빈 곳

아래는 현재 검증이 판정하지 않는다. 이것을 근거로 "검증 통과 = 문제 없음"이라고 말하지 않는다.

| 빈 곳 | 내용 |
|---|---|
| 화면 | 화면에 보이는 숫자 · 배지 · 레이아웃을 자동으로 확인하는 단계가 없다 |
| 제품 완료 기준 | `01 §7` 완료 기준과 테스트를 잇는 대응표가 없다 |
| 실행 수단의 보호 | `scripts/check-architecture.ts` · `scripts/reset-verify-db.ts` · `package.json`의 `verify`는 보호 경로가 아니다 |
| 승인 단위 | 보호 경로 승인은 경로 단위라서, 승인 뒤 같은 경로의 변경까지 통과한다 (`00-ssot.md §5`) |
